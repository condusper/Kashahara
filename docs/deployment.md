# Deploying Kashahara to production

This guide deploys the API to [Render](https://render.com) with a managed
PostgreSQL database, a shared Redis-compatible Key Value instance, HTTPS,
health checks, and automatic migrations. It then builds the Android app with
EAS and connects it to the deployed API.

The mobile app is not hosted on Render. Only the API and its data stores are.

---

## 1. What gets created

`render.yaml` defines three resources in the same Render region:

| Resource | Render type | Purpose |
| --- | --- | --- |
| `kashahara` | Web service (Node) | Express API, HTTPS, health checks |
| `kashahara-db` | Render Postgres | Users, wallets, ledger, purchases |
| `kashahara-redis` | Render Key Value | Shared rate-limit counters |

The web service runs:

```text
build:      npm ci --include=dev && npm run build:api
pre-deploy: node services/api/dist/migrate.js
start:      node services/api/dist/index.js
health:     /api/v1/health
```

`preDeployCommand` requires a paid web service plan. The blueprint uses the
smallest paid plans so migrations run automatically. For a real money-handling
launch, review Render's current plans and enable database backups/HA as your
volume grows.

## 2. Prerequisites

- A Git repository containing this project, pushed to GitHub, GitLab, or
  Bitbucket.
- A Render account with billing enabled.
- Paystack **live** keys (`sk_live_...`, `pk_live_...`) once you are ready to
  take real payments. Test keys work first and are safer for the first deploy.
- Bigisub API token and 4-digit transaction PIN.
- An Expo account and, for Play Store submission, a Google Play developer
  account with a service account JSON key.

The repository currently has no commits. Create the initial commit and push it
before connecting Render:

```bash
cd /root/kashahara/kashahara-vtu
git add .
git commit -m "Initial Kashahara production deployment"
git branch -M main
git remote add origin git@github.com:<your-account>/<your-repo>.git
git push -u origin main
```

`services/api/.env` and `services/api/.data/` are gitignored. Confirm with
`git status --short` before pushing; no secret should appear.

## 3. Deploy the API on Render

1. Open the Render Dashboard and choose **New > Blueprint**.
2. Connect the repository and select the branch you pushed (`main`).
3. Render detects `render.yaml`. Review the resources and region.
4. When prompted, enter the secrets marked `sync: false`:
   - `PAYSTACK_SECRET_KEY`
   - `PAYSTACK_PUBLIC_KEY`
   - `BIGISUB_API_TOKEN`
   - `BIGISUB_TRANSACTION_PIN`
5. Apply the blueprint.

`JWT_SECRET` is generated by Render and stored securely. Do not replace it
unless you intend to sign every user out.

The first deploy builds the shared workspace, compiles the API, runs the SQL
migrations, and starts the service.

### Service URL

The blueprint names the service `kashahara`, so the default URL is:

```text
https://kashahara.onrender.com
```

If Render assigns a different URL because the name is taken, update:

- the Paystack webhook URL below, and
- `EXPO_PUBLIC_API_URL` in `apps/mobile/eas.json`.

Optionally attach a custom domain such as `api.kashahara.app` in Render and use
that instead.

The native app does not use browser CORS. If you also deploy the Expo web build,
add `CORS_ORIGINS=https://your-web-origin` to the API service's environment
variables; otherwise the API only allows the local development origins.

## 4. Verify the deployment

```bash
curl -s https://kashahara.onrender.com/api/v1/health | jq
```

Expected values:

```json
{
  "status": "ok",
  "env": "production",
  "store": "postgres",
  "provider": { "name": "bigisub", "simulated": false },
  "paystackMode": "live",
  "simulatedFundingEnabled": false
}
```

If you deployed with test Paystack keys, `paystackMode` will be `"test"` until
you replace the key and redeploy.

In the Render **Logs** tab, confirm:

- `Using PostgreSQL store`
- `Connected to Redis for shared rate limiting`
- `Kashahara API listening` with `env: production`

There should be no `ALLOW_DEV_CODES`, simulated-payment, mock-provider, or
missing-database warnings.

Also confirm a protected endpoint rejects anonymous requests:

```bash
curl -i https://kashahara.onrender.com/api/v1/wallet
# HTTP/2 401
```

## 5. Configure Paystack

In the Paystack Dashboard, open **Settings > API Keys & Webhooks** and set:

```text
https://kashahara.onrender.com/api/v1/webhooks/paystack
```

Enable at least the `charge.success` event. The webhook is verified with
`PAYSTACK_SECRET_KEY`; no separate webhook secret is required.

The mobile app redirects successful payments back to the app with the
`kashahara://funding/{reference}` deep link configured in `render.yaml`. The API
also accepts the app's own `kashahara://funding` callback from the mobile
client.

Before taking live money:

1. Deploy with test keys.
2. Fund a wallet with a Paystack test card.
3. Confirm the app returns automatically and the wallet is credited.
4. Replace the test secret/public keys with live keys in Render.
5. Redeploy and repeat with the smallest live amount you are comfortable with.
6. Confirm the webhook delivery in the Paystack dashboard shows `200`.

Never set `ALLOW_SIMULATED_PAYMENTS=true` or `ALLOW_DEV_CODES=true` in
production. The API refuses to start with simulated payments enabled in
production, and the blueprint sets both to `false`.

## 6. Confirm the live supplier

Bigisub delivers airtime and data. Electricity, cable TV, and exam PINs are
still not wired through the live adapter and are refunded; see
[production-readiness.md](production-readiness.md).

From the Render **Shell** for the API service, verify the supplier credentials
without moving money:

```bash
npm run bigisub:check --workspace @kashahara/api
```

This uses `tsx` and therefore requires the dev dependencies installed by the
build command. If the shell image does not retain them, run the equivalent
check locally against the same credentials instead.

Then make one small live airtime purchase from the app and confirm the order
reaches `successful` in the Render logs and the supplier dashboard.

## 7. Build the Android app

Install and link EAS once:

```bash
cd apps/mobile
npx eas-cli login
npx eas-cli init
```

`eas init` writes `extra.eas.projectId` into `apps/mobile/app.config.js`.
Commit that change.

The `eas.json` file has two profiles:

- `preview`: internal APK for testers, pointing at the production API.
- `production`: Play Store build (AAB), auto-incremented version.

`cli.appVersionSource` is `remote`, so EAS initializes the remote version from
`android.versionCode` in `app.config.js` and increments it for each production
build. No manual version bump is needed.

Build:

```bash
npx eas-cli build --platform android --profile preview
# or, for the Play Store:
npx eas-cli build --platform android --profile production
```

The API URL is compiled into the bundle from
`EXPO_PUBLIC_API_URL` in `eas.json`. To point a build somewhere else, override
it:

```bash
EXPO_PUBLIC_API_URL=https://staging-api.example.com/api/v1 \
  npx eas-cli build --platform android --profile preview
```

For local development against the deployed API:

```bash
EXPO_PUBLIC_API_URL=https://kashahara.onrender.com/api/v1 npm run dev:mobile
```

### Submit to Google Play

Create a Google Play service account with the **Release manager** role, download
its JSON key, and upload it to EAS:

```bash
npx eas-cli submit --platform android --profile production
```

The first submission must be uploaded manually to Play Console to create the
app listing. Later submissions can use `eas submit`.

## 8. Operations

### Deploying updates

Push to the connected branch. Render rebuilds, runs migrations, and swaps
instances with zero downtime. If the build or migration fails, the previous
version keeps serving traffic.

### Migrations

Migrations are SQL files in `services/api/src/migrations`. The build copies them
to `dist/migrations`; `preDeployCommand` applies any that are not already in
`schema_migrations`.

To run them manually from the Render Shell:

```bash
node services/api/dist/migrate.js
```

Never edit or delete an applied migration. Add a new file instead.

### Scaling past one instance

Redis-backed rate limiting is already enabled through `REDIS_URL`. If you
increase `numInstances`, keep `REDIS_URL` set; without it each instance keeps
separate counters. The database connection pool is per instance (`max: 10`).

### Backups and restores

Enable Render Postgres backups on a paid plan. Test a restore into a separate
database before relying on it. Wallet balances and the ledger are the most
important data in the system.

### Secret rotation

- `PAYSTACK_SECRET_KEY`: update in Render, redeploy, update the Paystack
  dashboard if the key pair changes.
- `BIGISUB_API_TOKEN` / `BIGISUB_TRANSACTION_PIN`: update in Render and
  redeploy.
- `JWT_SECRET`: rotating it invalidates every access and refresh token, signing
  all users out.
- `DATABASE_URL` / `REDIS_URL`: managed by Render; do not paste them into logs
  or tickets.

### Rollback

Use Render's **Rollbacks** tab to redeploy a previous commit. Database
migrations are forward-only; a rollback that depends on an older schema may
need a manual migration.

## 9. Production checklist

- [ ] Repository pushed; no `.env`, `.data`, keys, or tokens committed.
- [ ] Render blueprint applied with paid web, Postgres, and Key Value plans.
- [ ] `/api/v1/health` returns `env: production`, `store: postgres`,
      `provider.simulated: false`, `simulatedFundingEnabled: false`.
- [ ] Render logs show PostgreSQL and Redis connected, with no dev warnings.
- [ ] Paystack webhook points at the Render URL and returns `200`.
- [ ] Test funding returns to the app automatically and credits the wallet.
- [ ] Live funding tested with a small amount.
- [ ] One small live airtime purchase succeeds through Bigisub.
- [ ] `ALLOW_DEV_CODES=false` and `ALLOW_SIMULATED_PAYMENTS=false`.
- [ ] Email/SMS delivery provider wired before disabling dev codes in
      non-production builds (still an open item).
- [ ] Database backups enabled and a restore tested.
- [ ] EAS production build installed from Play internal testing.
- [ ] Error monitoring and uptime alerts configured (Render notifications or an
      external service).

## Remaining launch gaps

Deployment does not close every product gap. Still required before a public
launch:

- Real email and SMS delivery for verification and password reset.
- Live electricity, cable TV, and exam PIN purchases.
- A support/refund runbook for uncertain supplier outcomes.
- Google Play listing assets, privacy policy, and data-safety form.

See [production-readiness.md](production-readiness.md) for the full list.
